## [P1] 下载重试继续使用失效的签名链接（复核仍存在）

- 位置：`src/main/audio-cache.js:185`，关联 `src/main/api.js:124`。
- 触发：解析接口成功返回音频地址，但 CDN 返回 403，随后点击收藏页“重试”。
- 原因：`retry()` 只清除下载失败记录；成功解析的地址仍在内存及磁盘中缓存 20 分钟。下一次 `ensure()` 再调用解析器时命中同一个旧地址。
- 复现：调用实际 API 缓存模块和下载队列，模拟解析器每次请求可生成新的签名地址、CDN 对旧地址返回 403。首次下载及点击重试后，两次下载都请求 `signed-1.mp3`；实际解析请求只有 1 次，失败数仍为 1。
- 影响：链接过期或临时失效后，即使重新解析能够得到新地址，用户主动重试仍可能持续失败。该问题不能解释所有音源的所有下载失败。
- 建议：提供歌曲、音源和音质对应的 URL 缓存失效入口，覆盖内存及磁盘缓存；遇到明确的链接失效响应时，在现有共享限流下刷新并有限重试，保留完整本地音频。

## [P1] 媒体实际加载失败绕过自动换源（复核仍存在）

- 位置：`src/renderer/src/player.js:392`。
- 触发：解析接口返回 URL，实际音频请求遭拒绝，或浏览器无法解码文件，触发 `audio.error`。
- 原因：`tryAltSources()` 仅由 `loadAndPlay()` 获取地址的异常路径调用；媒体错误处理器直接在 900ms 后跳到下一首。
- 复现：调用当前播放器模块，先成功获取音频地址，再触发媒体错误并执行其定时器。其他音源搜索次数为 0，队列索引从 0 变为 1。
- 影响：同一首歌在其他音源可用时仍会被跳过；该处理器也没有检查原本是否处于暂停状态，暂停时重新加载音质发生媒体错误也会触发自动跳歌。
- 建议：让媒体错误进入有次数限制的恢复流程，先刷新链接，再按歌名和歌手匹配其他音源；全程验证播放 token 和播放意图，全部失败后再决定是否跳歌。

## [P2] 启动后首次播放丢失保存的续播位置（复核仍存在）

- 位置：`src/renderer/src/player.js:280`，关联 `src/renderer/src/App.vue:112`。
- 触发：保存播放进度后重启，点击播放。
- 原因：启动只恢复界面中的 `player.position`。首次播放因为 `audio.src` 为空，调用 `loadAndPlay(true)`，没有传入保存的位置；该函数默认从 0 开始。
- 复现：按照启动流程设置队列及保存位置 73 秒，调用 `togglePlay()` 并触发元数据就绪。界面及实际音频位置均变为 0 秒。
- 影响：用户看到恢复的进度，但真正播放从头开始。
- 建议：明确区分恢复上次歌曲与选择新歌曲；恢复首次播放时传入保存位置，新选歌曲保持从 0 开始。定位应在元数据就绪后完成。

## [P2] 返回搜索历史后，在途结果混入另一查询（新增）

- 位置：`src/renderer/src/store.js:535`，关联 `src/renderer/src/store.js:481`。
- 触发：完成搜索 A，发起搜索 B，在 B 返回之前点击顶部返回按钮回到 A。
- 原因：历史导航覆盖 `ui.search`，却没有使 `searchSeq` 失效。B 返回时通过序号检查，向当前已恢复的 A 列表追加 B 的结果，并覆盖 A 对应的历史记录。
- 复现：A 返回 `A-result`；B 使用受控延迟请求。返回 A 后释放 B 的响应，最终查询文字仍为 A，结果列表却变成 `[A-result, B-result]`。
- 影响：查询名称、结果和分页状态不再对应，旧历史也被污染；在限流或慢网络下更容易触发。
- 建议：历史切换时使在途搜索失效并清理加载状态；响应只更新其所属查询或历史快照，不能仅依赖全局最新搜索序号来更新可变的 `ui.search`。

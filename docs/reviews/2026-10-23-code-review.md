## 需要处理的问题

### [P1] 下载重试没有刷新已失效的音频链接

位置：`src/main/audio-cache.js:185`、`src/main/api.js:124`。

音频地址的成功结果缓存 20 分钟。CDN 返回 403 后，下载器记录失败；“重试”只清空下载失败记录，解析器仍返回之前缓存的地址。签名链接过期等情况下，即使重新解析本来可以取得可用地址，重试仍会请求同一个失效地址。

受控复现结果：首次下载和点击重试后都失败，实际只调用解析器一次，两次下载请求均使用 `signed-1.mp3`。复现中的解析器第二次调用会返回可用的新地址，但该调用没有发生。

建议：为 URL 缓存提供定向失效入口。遇到 403/410 等失效链接信号时，在共享限流约束下重新解析并有限重试，保留完整音频缓存和收藏数据。

### [P1] 实际媒体加载失败不会自动换源

位置：`src/renderer/src/player.js:392`。

自动换源仅在获取音频地址抛错时运行。接口成功返回 URL，但实际请求被 CDN 拒绝或浏览器无法解码时，`audio.error` 处理直接安排 900ms 后跳到下一首，没有尝试同曲目的其他音源。

受控复现结果：先成功取得地址，再触发真实播放器模块的音频错误事件，其他音源搜索次数为 0，执行错误定时器后队列从第 1 首跳到第 2 首。

建议：让媒体错误也进入受播放 token 保护的恢复流程，先刷新同源链接，再尝试已匹配的其他音源；限定重试次数，全部失败后再跳过，避免陈旧请求覆盖用户刚选的歌曲。

### [P2] 重启后显示保存的进度，首次播放却从零开始

位置：`src/renderer/src/App.vue:111`、`src/renderer/src/player.js:280`。

启动时只把 `lastTime` 写入界面进度，未加载音频。首次点击播放时，`togglePlay()` 调用未传入 position 的 `loadAndPlay(true)`，该函数使用默认值 0，覆盖已恢复的进度。

受控复现结果：保存并展示 73 秒，首次播放和媒体元数据就绪后实际播放位置为 0 秒。

建议：区分“恢复上次播放”和“选择新歌曲”，首次恢复播放传入保存的位置；新选曲目仍从零开始。
